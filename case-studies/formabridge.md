## 담당 범위

- 4인 팀에서 풀스택과 배치 자동화를 맡음
- 머지 커밋을 제외한 전체 커밋 184건 중 53건을 담당함
- 서비스 배포(Dockerfile · `deploy.yml` · k8s 매니페스트)는 팀장 주도로 만듦
- 내 몫은 Spotify ID 백필 배치 스크립트와, 그것을 K8s Job으로 실행하는 공통 러너 · 워크플로 작성이었음

| 영역 | 작업 |
|---|---|
| 기능 | 메모(오늘의 곡 기록) · 검색(노래·사용자·메모) · 팔로우의 서버 읽기·쓰기 진입점(Remix loader·action), DB 함수, Prisma 모델과 마이그레이션, 화면까지 구현함 |
| 인증 | Google OAuth + JWT 인증과 페이지 접근 권한 제어를 구현함 |
| 외부 연동 | 음악 검색 API(MusicBrainz) 연동, Spotify 참조 키 저장과 재생 위젯 표시를 구현함 |
| 화면 | 프로필·핸들 설정, 모바일 하단 내비게이션 고정과 페이지 폭 정리를 맡음 |
| 배치 | Spotify ID 백필 배치 스크립트와, 그것을 GitHub Actions에서 K8s Job으로 실행하는 공통 러너 · 워크플로를 작성함 |

## 외부 API를 인터페이스 뒤에 둠 <!-- kind: 결정 -->

- 곡을 검색해 화면에 보여주는 기능에서 외부 API를 처음 직접 연결함
- 처음에는 키 없이 사용할 수 있는 MusicBrainz를 씀
- API를 붙이면서 **코드끼리 주고받을 데이터 형태인 인터페이스를 먼저 둠**
  - 제목 · 아티스트 · 앨범 등 화면에서 쓸 곡 정보의 형태를 정의함
  - 외부 응답을 그 형태로 바꾸는 구현과 검색을 호출하는 코드를 나눔
- 화면과 서버의 읽기 진입점은 검색 호출부를 거치도록 둠

- 넉 달 뒤 다른 팀원이 MusicBrainz를 Spotify로 교체함
  - MusicBrainz 구현 파일을 지우고 Spotify 구현 파일을 추가함
  - 그때 검색 호출부인 `SearchMusic.ts`의 변경은 3줄 추가 · 3줄 삭제였음

**이 판단의 한계**

- 같은 교체에서 검색 화면 쪽 코드는 크게 바뀜
  - 호출부 한 파일의 변경량을 교체 전체의 변경량으로 볼 수는 없음
- 초기 인터페이스에는 MusicBrainz의 곡 식별자인 `mbid?`가 남아 있었음
  - 공통으로 쓸 형태에 특정 서비스의 식별자가 들어간 점은 당시 놓침

## 남의 수정 페이지가 열렸음 <!-- kind: 틀림 -->

- 프로필과 설정 화면은 URL에 사용자 번호가 들어가는 형태였음
- 로그인만 확인하고 소유 여부는 `// TODO` 주석으로 미뤄 둔 채 화면이 이미 동작하고 있었음
- 개발 중 직접 URL의 사용자 번호를 바꿔 들어가 보니 다른 사람의 수정 페이지가 열리고 수정도 됐음

- **로그인한 사람인지와 그 자료를 수정할 권한이 있는지는 다른 문제였음**
  - 로그인 정보가 없으면 로그인 실패 화면으로 보내도록 함
  - 로그인한 사람이 남의 자료에 접근하면 접근 권한이 없다는 뜻의 403 응답을 반환하도록 함
- 두 경우를 가르는 검사 함수를 하나 작성함
- 설정 · 핸들 수정 · 오늘의 곡 추가 · 메모의 서버 읽기·쓰기 진입점마다 검사를 붙임
  - URL의 사용자 번호를 받지 않던 함수는 그 값을 받도록 인자부터 바꿈
- 소유권 확인을 미뤄 둔 `// TODO` 주석을 지우고 실제 검사로 바꿈

## Spotify 데이터를 복제하지 않음 <!-- kind: 결정 -->

- 곡에 재생 가능한 미리듣기를 제공한다는 기능과 요구사항은 직접 정함
- Spotify의 곡 정보를 통째로 복제하는 대신 참조 키인 `spotifyId`만 저장하는 쪽을 택함
- 화면을 그릴 때 재생 위젯을 받아오는 oEmbed 방식과 키가 없을 때의 처리는 에이전트가 제안한 것을 검토해 승인함
  - 키가 있으면 커버 · 미리듣기 · Spotify 연결이 들어 있는 재생 위젯을 받아 표시함
  - 키가 없으면 DB에 저장된 제목 · 아티스트를 대신 보여주도록 함

- 이전 곡을 채우는 백필도 `spotifyId` 하나만 갱신함
  - DB의 제목 · 아티스트는 건드리지 않음
  - 화면이 한국어로 보이게 된 것은 제목을 일괄 변경해서가 아니라 Spotify 위젯을 표시했기 때문임

**이 판단의 한계**

- 곡을 볼 때마다 외부 호출이 하나씩 붙음
- 외부에서 받은 HTML을 그대로 화면에 넣으면서 응답 출처를 확인하는 검증은 빠져 있었음
- 지금이라면 목록에 필요한 최소한의 곡 정보는 저장하고, 재생 위젯은 상세 화면에서만 부르도록 나눌 것임

## 컬럼 추가 이전에 쌓인 곡의 빈 값을 배치로 채움 <!-- kind: 결정 -->

- `spotifyId` 컬럼을 추가한 뒤 등록되는 곡은 저장할 때 값이 채워지도록 해 둠
- 그 전에 쌓인 곡만 제목 · 아티스트는 있고 참조 키가 비어 있었음
- 곡마다 외부 API 호출이 필요해 서비스 요청 흐름에서 처리할 수 없어 별도 배치로 분리함
  - **배치 쪽이 한 번 돌리는 작업이었음**
- 곡 제목 · 아티스트로 Spotify를 검색해 참조 키를 채우는 스크립트를 작성함
- 그 스크립트를 GitHub Actions에서 Kubernetes의 일회성 실행 단위인 K8s Job으로 돌리는 공통 러너 · 워크플로도 작성함
  - 하나의 PR에 백필 스크립트 · 공통 러너 · 배치 이미지 정의 · Job 템플릿 · 워크플로 둘을 함께 담음

- 실제로 쓰기 전에 **검색에 넣을 제목 · 아티스트를 DB에서 제대로 읽어오는지부터 확인함**
  - DB에 쓰지 않고 읽어 온 곡 정보와 변경 예정 값을 출력하는 `DRY_RUN` 모드로 확인함
- 실행 입력이 없을 때 안전한 값을 정하는 곳은 워크플로였음
  - 워크플로에서 실행 입력을 생략하면 DB에 쓰지 않는 값이 전달됨
  - 스크립트는 전달받은 값이 문자열 `'true'`인지에 따라 출력만 할지 실제로 쓸지 고름
  - 스크립트를 환경변수 없이 직접 실행하면 실제 쓰기로 들어감

- 실행 시작 시 연결된 DB와 스키마 이름을 출력하도록 함
- 참조 키가 비어 있는 곡만 대상으로 삼아 이미 채워진 곡은 재실행에서 제외함
- DB 접속 문자열을 가려 출력하고, 외부 호출 사이에 간격을 둠
- 곡 단위로 실패를 처리해 한 곡의 오류가 전체 작업을 멈추지 않도록 함

**이 판단의 한계**

- 대상 조회에 상한만 있고 다음 묶음을 이어 읽는 반복은 없음
  - 대상이 상한을 넘으면 배치를 반복 실행해야 함

## 검증하려면 머지해야 하고, 머지하려면 리뷰가 필요했음 <!-- kind: 틀림 -->

- 배치 워크플로는 `main`에 변경이 들어와야 실행되도록 돼 있었음
- `main`은 리뷰를 받아야 머지할 수 있었고, 새벽에는 리뷰해 줄 사람이 없었음
- 워크플로 문법 · 비밀값 이름 · 권한 같은 문제는 실제로 실행해야만 드러나는 종류였음
  - 고친 것을 검증하려면 머지해야 하는데 리뷰를 기다리느라 실행할 수 없었음
- 병목을 직접 통제할 수 없는 대기 시간으로 보고 개인 저장소에 복사한 fork에서 같은 조건을 재현함
  - 값을 채운 뒤 직접 변경을 올리고 수동으로 워크플로를 실행함

- fork만으로 끝나지 않아 최종 통합은 팀 저장소에서 해야 했음
- 팀 저장소의 통합 작업은 11월 6일 저녁부터 7일 저녁까지 이틀에 걸쳐 진행됨
- Docker · Kubernetes · GitHub Actions는 이 배치 작업에서 처음 다룬 것이라 개념과 동작을 익히는 시간도 필요했음
- 여기에 **실제로 실행될 설정을 볼 수 없어 추측으로 반복한 시간**이 더해짐
  - 템플릿에 값을 채운 결과를 볼 수 없어 템플릿과 입력값 중 어느 쪽이 잘못됐는지 구분하지 못함
  - 한 줄씩 고치고 다시 실행하는 일을 반복함
- 값이 채워진 최종 설정을 로그에 출력하는 단계를 넣은 뒤에야 원인이 보이기 시작함

- 백필 완료 뒤에는 `main`에 변경이 들어올 때마다 다시 실행되지 않도록 자동 실행을 거두고 수동 실행만 남김
  - 마지막 되돌림 커밋은 일회성 작업의 자동 실행을 정리한 것이었음

**이 판단의 한계**

- fork만으로 작업을 끝내지는 못함
- 최종 통합 과정의 「수정중」 커밋이 `main` 이력에 남음

## 자격증명 보관과 로그 처리는 지금이라면 다르게 할 것임 <!-- kind: 남김 -->

- 배치를 검증하면서 팀 클러스터에 접속하는 설정과 자격증명인 `KUBECONFIG`를 개인 fork의 Secret에 넣음
  - 데이터를 바꾸지 않는 모드였지만 팀 인프라 자격증명이 팀의 접근 통제 밖에 놓였음
- 지금이라면 읽기 전용 계정과 별도 작업 구역인 네임스페이스를 준비하고, 검증이 끝나면 자격증명을 회수할 것임
- 2026년 8월에 fork에 남아 있던 Secret을 삭제함

- DB 접속 문자열은 마스킹 함수로 가렸지만 Spotify 액세스 토큰은 반복할 때마다 로그에 그대로 출력되고 있었음
- 비밀값을 가려야 한다는 것을 몰랐던 것이 아니라 다른 출력에 적용하지 못한 누락이었음
  - 한 곳에 마스킹 함수를 둔 것만으로 전체 로그가 가려지지는 않았음
  - 개인의 주의력이 아니라 체계로 막아야 할 일임
