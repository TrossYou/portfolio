## 바뀌어 온 순서

- PinLog(2026.07–08, 6인 팀)에서는 규칙 문서를 두고 시작해, 하나씩 지시하던 순차 작업에서 커밋 전 보고 · 승인 절차를 거쳐 병렬 작업으로 옮겨 감
  - 각 세션을 직접 상대하다 감독 창구 하나를 거치게 했다는 것이 당시 과정을 돌아본 본인 회고였음
- FINCH(2026.08–09, 5인 팀)에서는 감독 · 실행 · 학습 세 계층으로 나눔
  - 작업을 배정하고 검토하는 대화에서 모르는 개념을 공부하는 대화를 따로 뺌
- 취업 준비(2026.08–, 개인)에서는 에이전트가 쓸 재료를 근거 있는 경험 기록으로 한정함
  - 기록마다 근거와 확인 상태를 붙이고, 기록에 없는 경험은 쓰지 않게 함
- 기업 연계 팀 프로젝트(2026.10–, 진행 중)에서는 지휘 세션 하나가 티켓을 나눠 하위 에이전트에 맡기게 함
  - 관문은 실행 전 훅이 멈추게 하고, 채팅으로 묻는 범위는 main 머지로 좁힘

## 금지 옆에 허용되는 행위를 함께 적음 <!-- kind: 결정 -->

> 2026.07–08 · [프로젝트 기록](pinlog.md)

- 프론트엔드 기능 구현을 맡으며 에이전트에게 규칙 문서를 주고 작업시킴
- 문서에 있던 「프론트는 토큰을 저장하지 않는다」를 에이전트가 「재발급 로직 자체를 만들지 말라」로 읽음
  - 로그인 상태를 증명하는 토큰의 저장 금지가, 인증 실패 응답인 401을 받은 뒤 복구하는 동작까지 막은 셈이었음
  - 그 결과 401 복구가 통째로 빠짐
- 토큰 저장 금지는 유지하고, 혼동한 인접 행위를 같은 항목에 붙임
  - 재발급은 반드시 하되 토큰 값을 읽거나 보관하지 않는다고 함께 적음
- 이후 규칙도 금지만 쓰지 않고, 혼동하기 쉬운 행위 중 허용되는 것을 나란히 적는 형식으로 통일함
- 같은 오독은 다시 나오지 않았음

## 병렬화가 병목을 없앤 것이 아니라 나에게로 옮겼다고 판단함 <!-- kind: 틀림 -->

> 2026.07–08 · [프로젝트 기록](pinlog.md)

- 순서대로 지시하던 작업을 동시에 진행하려고 `git worktree`로 작업 공간을 나눔
  - 같은 저장소를 서로 다른 폴더와 브랜치에서 작업하게 하는 기능을 이용함
- 처음에는 공간을 나누는 것만으로 작업이 분리되지 않았음
  - 같은 기능을 중복 구현하는 일이 생김
  - 병렬 개발 서버의 접속 주소가 외부 서비스에 등록되지 않아 생긴 인증 오류를 코드 문제로 오인함
  - 앞선 브랜치를 변경 이력 하나로 합친 뒤, 그 위에서 시작한 브랜치에 충돌이 남음
- 작업 분할 기준을 폴더에서 **실제로 고칠 파일 목록**으로 바꿈
  - 티켓마다 대상 파일을 먼저 정하고, 파일이 겹치는 작업은 같은 작업 공간에서 순서대로 진행함
  - 파일이 겹치지 않아도 서로의 동작 조건에 영향을 주면 순서를 고정함
- 재분할 뒤 코드 병합 요청인 PR 3건의 파일 목록을 대조하니 교집합이 0이었음
  - 모두 충돌 없이 병합 가능한 `MERGEABLE/CLEAN` 상태였다는 것은 2026년 8월 당시 관찰값이었음
  - 이미 병합된 요청들이어서 현재 같은 상태값을 다시 조회할 수는 없음
- 그 뒤에도 세션마다 검토 · 실행 승인 · 다음 지시를 기다리는 일이 반복됐다는 것이 본인 회고였음
  - 여러 작업이 어디까지 갔는지 직접 따라가는 것도 어려웠다고 돌아봄
- 병렬화로 병목이 사라진 것이 아니라 내 응답과 검토로 옮겨 왔다고 판단함
- 모든 세션을 직접 상대하는 대신 감독 세션 하나를 거치게 함
  - 작업 배정 · 중간 검토 · 상태 관리는 감독 세션에 맡기고, 나는 그 창구와 소통하게 함

## 작업을 감독하는 자리에서 학습하는 자리를 따로 뺌 <!-- kind: 결정 -->

> 2026.08–09 · [프로젝트 기록](finch.md)

- 감독관 · 워커 두 계층으로 프론트엔드 구현을 시작함
  - 감독관은 작업 배정과 검토를 맡고, 워커는 나눠 받은 구현을 맡음
- 감독관에게 배정 · 검토 · 상태 관리가 모인 위에 개념을 묻는 학습 대화까지 섞였다고 회고함
  - 그 과정에서 설명을 나누는 자리가 필요했다고 판단함
- 대화창만 나누면 설명은 여전히 세션과 함께 사라지는 문제가 있었음
  - 학습 전용 에이전트인 튜터를 따로 두고, 설명을 팀 코드 저장소 밖의 학습 노트에 쌓게 함
- 감독 · 실행 · 학습 세 계층으로 나눠 운영함
  - 감독관은 작업 분해 · 배정 · 승인 관문 · 이슈와 병합 요청 상태를 맡음
  - 워커는 티켓별 작업 공간과 브랜치에서 구현을 맡음
  - 튜터는 모르는 개념을 설명하고 학습 노트를 남김

**이 판단의 한계**

- 역할을 나눈 뒤에도 지시를 많이 쓰는 것이 항상 도움이 되지는 않았음
- 디자인 시안 셋을 경쟁시키면서 기존 정보 구조를 가져다 쓰고 화면 부품의 이름 · 입력 형태는 방향 사이에 같게 유지하라는 제약을 함께 걸었음
  - 결과는 색과 그림자만 다르고 배치가 거의 같았음
  - 서로 다른 방향을 고르려고 만든 선택지를 내 제약으로 수렴시킨 판단 착오였음

## 기억 대신 근거가 붙은 기록만 재료로 쓰게 함 <!-- kind: 결정 -->

> 2026.08– · 개인

- 포트폴리오를 정리하다 내 기억이 실제 코드 · 커밋과 여러 곳에서 다르다는 것을 확인함
- 2026년 8월 초부터 경험을 하나씩 문서화하는 개인 저장소를 만들기 시작했다는 것이 본인 진술이었음
- 경험마다 근거 자료와 확인 상태를 붙임
  - 커밋 해시 · PR 링크 · 증빙 파일을 연결하고, 근거가 없거나 대조하지 못한 기록은 그 상태를 표시함
  - 직접 정한 것과 에이전트가 제안한 것을 구분하는 항목도 따로 둠
- 에이전트는 그 기록만 재료로 초안을 쓰게 함
  - 기록에 없는 경험은 쓸 수 없게 함

**이 판단의 한계**

- 기록을 만들었다고 내용 확인까지 끝난 것은 아니었음
  - 처음에 기록을 한꺼번에 만들며 다 읽어 보지 못했고, 형식도 바꾸면서 기록이 계속 수정되고 있다는 것이 본인 진술이었음
- 여러 기기를 써야 해 비공개 원격 저장소에 올려야 했다는 것이 본인 진술이었음

## 단계마다 묻는 승인을 main 머지로 좁힘 <!-- kind: 결정 -->

> 2026.10– · 기업 연계 팀 프로젝트

- Claude Code 지휘 세션이 티켓을 나누고 하위 에이전트에 구현을 맡기게 함
- 첫 작업에서 커밋 · 코드 올리기 · 병합 요청 생성 · 리뷰 답글을 단계마다 묻는 것이 병목이라고 짚음
- 에이전트가 제안한 「작업 묶음」 단위 승인을 받아들임
  - 선택지와 기각 이유의 정리, 실행 전 명령을 확인하는 훅 코드는 에이전트가 맡음
- 묶음으로 바꾼 뒤에도 질문이 이어져, 같은 날 채팅으로 묻는 범위를 **main 머지**로 더 좁힘
  - main 머지는 작업 브랜치의 변경을 팀의 기준 브랜치에 합치는 단계임
- 묻는 명령 목록은 규칙 문서가 실행 전 훅을 따르게 정함
  - 에이전트가 반대로 훅을 문서에 맞춰 줄이려 하자 멈추고, 훅의 목록을 문서에 옮기게 함
- 리뷰 대응도 매번 묻지 않고 진행한 뒤 보고하게 함
- main 머지는 내가 허락해도 리뷰어 승인이 없으면 진행하지 말고, 에이전트도 승인 상태를 확인하게 함

**이 판단의 한계**

- 에이전트에게 머지를 맡긴 구조에서 승인 · 리뷰 대화 확인의 빈틈이 사례마다 드러남
  - 승인 글에 남은 요청, 조회 시점과 값의 뜻, 답글이 새 리뷰 대화가 되는 경우까지 확인 대상이었음
- 직접 짚은 것은 놓친 리뷰 대화와 확인 결과를 보고하기 전에 머지한 순서였음
- 확인 절차가 빈 곳을 사례마다 메우게 했으며, 교훈 문장과 확인 방법의 정리는 에이전트가 맡음

## 화면이 어떻게 보이는지 판단하는 단계가 한 사람에게 남음 <!-- kind: 남김 -->

> 2026.09 · [프로젝트 기록](finch.md)

- 구현을 맡은 에이전트는 격리된 작업 공간에서 타입 검사 · 코드 규칙 검사 · 빌드까지 확인함
- 작업 기록 여러 건이 「브라우저로 실제 화면을 보지 못함」으로 끝났고, 실제 모양을 판단하는 단계가 나 한 사람에게 남음
  - 원격 디버깅으로 화면을 띄운 예외가 한 번 있어, 고정된 한계는 아니었음
- 자동 검사를 통과한 코드에서도 화면을 열어야 보이는 문제가 나옴
  - 보유 카드의 손익 색이 검정으로만 보였음
  - 시세가 없는 종목의 안내 문장이 크게 표시돼, 일부 값이 없는 상태가 전면 장애처럼 읽혔음
- 손익 색의 원인으로 댄 추정은 빗나갔고, 실제 원인은 에이전트가 찾음
- 화면 판단을 덜어 보려고 프로토타입과 구현을 비교하는 표도 쓰게 했으나 접음
  - 표가 화면 수정으로 제대로 이어지지 않았고, 없어진 화면 요소와 밀린 코드 위치를 그대로 가리키며 낡았음
- 프로토타입과 개발 서버 화면을 나란히 놓고 직접 보며 피드백하는 방식으로 돌아옴
- 한 사람이 빠지면 화면 판단 단계도 빠지고, 열어 보지 않은 화면의 결함은 남는 구조였음
  - 확인한 화면을 목록으로 남기는 일이 다음 과제로 남음

## 기여의 범위

| 내가 결정한 것 | 에이전트가 만든 것 |
|---|---|
| 금지 옆에 허용되는 인접 행위를 함께 적도록 함 | 규칙에 따라 작성한 구현 코드 |
| 모든 세션을 직접 상대하던 접점을 감독 창구 하나로 줄임 | 배정받은 작업의 구현 코드 |
| 작업을 감독하는 자리와 학습하는 자리를 나눔 | 워커의 구현과 튜터의 학습 노트 |
| 경험마다 근거와 확인 상태를 붙이고 그 기록만 재료로 쓰게 함 | 기록을 재료로 쓴 지원서 초안 |
| 기기를 오갈 때의 문제를 제기하고 제안된 방식의 구멍을 질문으로 짚음 | 동기화 훅 구조와 스크립트 |
| 기업 연계 프로젝트에서 채팅으로 묻는 범위를 main 머지로 좁힘 | 관문 훅 코드 · 선택지와 기각 이유 정리 |
